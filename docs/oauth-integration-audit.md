# Проверка интеграции VK ID: источники и сервер

Проверено 15 октября 2026. Локальные тесты проверяют реализацию, но не настройку
ресурса приложения ВК, DNS, сертификат или reverse proxy на VPS.

## Прочитанные официальные первоисточники

- [VK PHP SDK: User.php](https://github.com/VKCOM/vk-php-sdk/blob/master/src/VK/OAuth/User/User.php):
  начало входа на `https://id.vk.com/authorize`, обмен кода через POST
  `https://id.vk.com/oauth2/auth`; описан возврат `code`, `device_id`, `state`.
- [AuthorizeUrlParams.php](https://github.com/VKCOM/vk-php-sdk/blob/master/src/VK/OAuth/User/DTO/AuthorizeUrlParams.php):
  `response_type=code`, ID приложения, точный redirect URI, случайный state,
  PKCE S256 с URL-safe Base64 без padding и scopes, разделёнными пробелами.
  Обязательная промежуточная страница приложения в этой реализации не указана.
- [VK ID Web SDK: auth.ts](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/auth.ts)
  и [тесты авторизации](https://github.com/VKCOM/vkid-web-sdk/blob/master/__tests__/auth/auth.tests.ts):
  есть отдельные режимы redirect и popup/new tab; параметр `origin` добавляется
  для режима, отличного от redirect. Нельзя считать произвольную замену
  Referer исправлением ошибки кабинета ВК.
- [VK ID Web SDK: построение URL](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/utils/url/url.ts):
  веб-SDK добавляет собственные параметры `sdk_type`, `app_id`, версию SDK.
  Они не являются доказательством необходимости выдавать наш серверный адаптер
  за этот SDK: официальный PHP-адаптер формирует запрос без этих метаданных.

Страницы документации кабинета на `id.vk.com` и `id.vk.ru` не удалось открыть
из рабочей среды: прокси вернул 403. Поэтому здесь описаны фактически прочитанные
официальные исходники и тесты; доступ к документации кабинета не заявляется.

## Что известно о текущей установке

- Пользователь проверил сервер: приложение `54825414`, провайдер `vkid`,
  callback `https://bot.itiscat.ru/oauth/vk/callback`.
- Подсказка кабинета ВК прямо разрешает начальную точку в базовом домене для
  поддоменов. Значение `.itiscat.ru` само по себе не является ошибкой.
- На скриншоте callback показывает обычный сайт вместо обработчика бота,
  а браузер отмечает HTTPS как небезопасный. Точная причина предупреждения
  определяется проверкой TLS; один скриншот не устанавливает причину.
- Из этого нельзя заключить, что исходная ошибка домена в ВК вызвана именно
  reverse proxy. Это два отдельных этапа, оба требуют проверки.

Промежуточная страница из коммита `089385b` отменена: её необходимость и
способность устранить ошибку домена не были подтверждены.

## Сначала проверить реальный callback, без авторизации и без секретов

Бот должен оставаться запущенным. Откройте **второе SSH-подключение**, чтобы
не вводить команды в занятый процесс Python. Для стандартного `OAUTH_PORT=8081`:

```sh
curl -sS -i --max-time 15 http://127.0.0.1:8081/oauth/vk/callback
```

Затем проверьте внешний адрес с обычной проверкой сертификата:

```sh
curl -sS -i --max-time 15 https://bot.itiscat.ru/oauth/vk/callback
```

Это запросы без `state` и `code`: они не расходуют ссылки и не публикуют посты.
От настоящего обработчика ожидаются HTTP **400**, `Cache-Control: no-store`,
`Referrer-Policy: no-referrer` и текст «Ссылка подключения недействительна.».
400 здесь означает, что обработчик доступен и правильно отверг пустой запрос.

| Результат | Следующий шаг |
| --- | --- |
| Локально connection refused | Проверить, запущен ли бот, включён ли OAuth и какой задан порт. |
| Локально ожидаемый 400, снаружи HTML обычного сайта | Проверить DNS и маршрут callback в выбранном виртуальном хосте веб-сервера. |
| Снаружи ошибка TLS | Проверить сертификат для `bot.itiscat.ru`, цепочку доверия и выбранный HTTPS virtual host. |
| Снаружи 301/302 | Проверить `Location`; callback не должен уходить на другой сайт или терять параметры кода. Не следовать редиректам вслепую. |
| Локально и снаружи одинаковый ожидаемый ответ | Callback достигает приложения; переходить к живой проверке входа ВК. |

Не добавляйте `-k` для обхода проверки сертификата. Проверяйте, что DNS
`bot.itiscat.ru` указывает на нужный сервер. Если TLS заканчивается на внешнем
прокси, настраивайте маршрут там, а не только на VPS.

## Исправление маршрута после определения фактической конфигурации

Для nginx нужный участок внутри **существующего HTTPS server-блока, который
обслуживает `bot.itiscat.ru`**, приведён в
[шаблоне](../deploy/oauth-nginx.conf.example). Ключевая строка:

```nginx
location = /oauth/vk/callback {
    access_log off;
    error_log /dev/null;
    proxy_pass http://127.0.0.1:8081;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto https;
    proxy_connect_timeout 5s;
    proxy_read_timeout 120s;
    add_header Referrer-Policy no-referrer always;
}
```

Сначала найдите реальную конфигурацию и сохраните её копию. Не подключайте
второй конфликтующий server-блок и не заменяйте целиком работающий сайт.
Не переносите пример путей сертификатов без проверки, что файлы существуют.
После осмысленного изменения nginx:

```sh
nginx -t
```

Только при успешной проверке:

```sh
systemctl reload nginx
```

После этого повторите оба запроса callback. Если используется не nginx,
аналогичный маршрут настраивается в фактическом reverse proxy.

## Затем отдельно проверить авторизацию ВК

Запросите новую ссылку в боте. Если ВК по-прежнему показывает ошибку домена
до возврата на callback, проверьте настройки именно ресурса `54825414` в
кабинете VK ID: платформу, сохранённые домены и redirect URI. При отсутствии
доказанной причины не меняйте провайдер, scopes и ключи наугад.

Для `vkid` код использует PKCE без client secret. Вариант `vk_api` использует
client secret и другой endpoint; переключение требует подтверждения, что
приложение поддерживает этот flow. Сервисный ключ приложения не заменяет
пользовательское согласие и не даёт сам по себе права публикации.

## Ошибка API после возврата с кодом

Сообщение «Проверка подключения ВК: ИМЯ_МЕТОДА, код API ЧИСЛО» означает, что
обмен кода уже выполнен, но последующая проверка не прошла. Проверки выполняются
по порядку: `account.getProfileInfo` (личность), `account.getAppPermissions`
(wall/photos), `groups.getById` (права в сообществе). Отказ любого из методов
нельзя автоматически считать отсутствием wall/photos: нужны конкретные метод
и код. Если API-проверка не прошла, ключ не сохраняется.

В диагноз выводятся только имя метода и числовой код, без `error_msg`, токенов,
параметров запроса и сырого ответа ВК. Запрашивать пользовательский ключ в чате
для этой диагностики не требуется. Изменять scopes или обходить проверки
личности и прав ради успешного сообщения нельзя.
